## How the numbers are tied to their meaning

Every result is a named macro in `numbers.tex`, generated by `make_numbers.py` from:

| Result file | What it holds |
|---|---|
| `results/cobar/confirmatory/confirmatory_analysis.json` | frozen confirmatory analysis; the SHA-256 of `FROZEN_CONFIG.json` is checked |
| `results/cobar/confirmatory/S1_breakdowns.json` | exploratory breakdowns by delta type and size |
| `results/cobar/pilot/*/analysis.json`, `regimes_analysis.json` | development pilots |
| `results/research_extension/dev_e5c/cobar_certificate_diagnostic.jsonl` | offline replay of IAIP-SR development runs |
| `results/cobar/oracle_campaign.json`, `results/cobar/audit_intermediate.json` | exact-oracle campaign and intermediate-incumbent audit |
| `results/cobar/confirmatory/S1_primary/runs` | candidate behaviour (rounds per instance, local-window time) |

For each macro, `claims.json` records:
- source file;
- setting;
- algorithm;
- comparator;
- metric (PI or final gap);
- statistic (relative difference and its sign, streams won/lost, bootstrap interval, Holm-adjusted p);
- aggregation;
- table.

Tables are generated from the same registry, so a cell cannot hold a number from the wrong row or setting.

`check_claims.py` fails if:
- a claim macro is undefined;
- or a result-like literal (percentage, decimal fraction, ratio, p-value) appears in the text outside the allow-list of design constants.

**Current result:** 72 claim macros used, 0 undefined, 0 hand-typed result literals. `claim_map.md` lists each used macro with its metadata.

**A bug in the checker itself was found and fixed.** The first version dropped the rest of every line after an escaped `\%`, so it checked only part of the text.
